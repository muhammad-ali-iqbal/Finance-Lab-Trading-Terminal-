SimTrader
Internal Security Audit Report
Code-Level Review for Institutional Deployment


Overall Risk Rating:  ELEVATED






Finance Lab · School of Business Studies
Prepared by: Muhammad Ali Iqbal
Classification: Internal — for IBA ICT deployment review

1. Executive Summary
This report documents an internal, code-level security audit of SimTrader, an educational paper-trading platform built for the IBA Finance Lab, ahead of an institutional (university ICT) deployment review. The audit examined the full stack — the Go/Fiber backend, the React/TypeScript frontend, the Python PSX data tracker, and the Docker deployment configuration — across nine security dimensions, with each finding independently re-verified against the current source code. It is important context that SimTrader handles no real money, no payment data, and only minimal personally identifiable information (student names and email addresses); the impact of any given issue should be weighted against that reality.
Overall the platform demonstrates a solid security foundation: passwords are bcrypt-hashed (cost 12), all database access is parameterized (no SQL injection), JWTs are signed with a pinned HMAC method and refresh tokens are SHA-256 hashed and rotated, containers run as non-root, secrets are sourced from environment variables and kept out of git, and authentication endpoints are rate-limited. Several meaningful issues were identified and a number were already remediated during the audit cycle — notably the removal of an insecure shared-secret default on the Go backend, switching to a constant-time secret comparison, defaulting the runtime environment to "production", and confirming there is no student-to-admin privilege-escalation path. The residual open issues are concentrated in deployment hardening (no TLS termination, a publicly known default admin password that still ships when admin credentials are unset, an insecure secret default that persists on the Python tracker side) and in the correctness/robustness of the Challenge reconciliation engine (non-transactional fills that can leave balances inconsistent or double-charge under concurrency). None of these expose real financial assets, but they are genuine risks for an internet-facing deployment and several should be closed before the platform is exposed beyond the lab network.
Overall Risk Rating: Elevated
The rating reflects open findings only; remediated items are excluded as they no longer contribute risk. The platform is not handling money or payment data and collects only minimal PII, which caps worst-case impact and argues against a "High" or "Critical" rating. However, several genuine internet-facing risks remain open: the entire stack speaks plaintext HTTP with no TLS termination (credentials and JWTs traverse the wire in cleartext); a publicly known default admin password (admin@simtrader.app / ChangeMe123!) still ships and the container boots with it active when ADMIN_* env vars are unset; the Python tracker retains an insecure 'dev-internal-secret' default for the secret that gates an endpoint which mutates competition balances; and the Challenge reconciler performs non-transactional, non-idempotent order fills that can corrupt cash/position state or double-fill under realistic concurrency. These are operationally significant for a public deployment but are largely closable with configuration and bounded code changes, and the most damaging financial-corruption paths affect only simulated balances. That combination — real internet-facing exposure and data-integrity defects, bounded by the absence of real assets — places the platform at "Elevated" rather than "High". Closing the TLS, default-admin, and tracker-secret items plus making reconciliation transactional would bring residual risk down to "Moderate" or "Low".
Findings at a Glance
2. Scope & Methodology
Scope
In scope: a static, code-level review of the SimTrader monorepo as it currently stands, covering (1) the Go/Fiber backend (authentication, authorization, session management, order/portfolio/challenge logic, configuration, database access), (2) the React/TypeScript frontend (build/dependency posture, nginx config), (3) the Python PSX data tracker (scraper, scheduler, backend integration), and (4) the Docker/Compose deployment topology, migrations, and entrypoint. Nine dimensions were assessed: Authentication & Session Management; Authorization & Access Control; Secrets & Configuration Management; Input Validation & Injection; Infrastructure & Containers; Network Exposure & CORS; Data Handling & Privacy; Dependencies & Supply Chain; and External Integration & Availability. Out of scope / not performed: external/dynamic penetration testing, runtime/DAST scanning, fuzzing, load and denial-of-service testing, social-engineering assessment, third-party dependency CVE testing beyond version review at the knowledge cutoff, and any assessment of the production hosting environment (cloud account, network perimeter, managed database, external reverse proxy) which was not available for inspection. Dependency advisory status is asserted as of the analysis knowledge cutoff and is time-bounded.
Methodology
The audit used a multi-agent code-review approach: specialized review passes were conducted across the nine security dimensions, and every candidate finding was then subjected to independent adversarial verification against the current source — re-reading the cited files and line numbers, confirming or correcting severity and remediation status, and discarding or downgrading claims that did not hold up (for example, tempering an over-stated stored-XSS framing on avatar upload, correcting a CORS finding's claim that a typo could silently re-enable permissive behavior, and re-classifying git-hygiene state that the initial pass mis-described). Verification also raised severity where warranted (for example, the reconciler concurrency double-fill path was raised to high after confirming all three trigger paths and the absence of any lock or status guard). Positive controls were verified with the same rigor as defects and are recorded so the report reflects the platform's real posture, not only its gaps. The review is static only; no code was executed against a live instance and no external testing was performed.
3. Key Security Strengths
The following controls were independently verified as correctly implemented and represent the platform's existing security posture:
- Passwords are hashed with bcrypt at cost factor 12 and the hash field is never serialized to API responses (json:"-"); no plaintext passwords are persisted.
- All database access is parameterized via pgx positional placeholders across every repository, including the one dynamically-built clause and array-membership queries — no SQL injection vector exists; bulk CSV insert uses typed CopyFrom with static columns.
- JWT signing method is pinned to HMAC, rejecting alg=none and RS256->HS256 key-confusion attacks; access tokens are short-lived (15m) and refresh tokens are SHA-256 hashed, rotated on each use, and revocable.
- No student-to-admin privilege-escalation path: registration is invite-only with a server-assigned role, the JWT role derives solely from the database row, and refresh re-reads the user and re-checks blocked status.
- Strong authorization model: every admin route is gated by chained RequireAuth + RequireRole middleware that fails closed; per-user resources (orders, portfolio, challenge participation) are scoped by the JWT user ID, preventing IDOR; challenge endpoints enforce enrollment.
- Authentication hardening against enumeration and brute force: dummy bcrypt compare on unknown email, constant-response forgot-password, generic error messages, and a 10 req/min/IP rate limiter on login/register/forgot/reset.
- Secrets are required environment variables (DATABASE_URL, JWT_ACCESS_SECRET, JWT_REFRESH_SECRET, INTERNAL_SECRET) with fail-closed startup and no insecure defaults on the Go side; ENV defaults to 'production'; no real secret is tracked in git (only .env.example placeholders).
- Internal EOD webhook uses crypto/subtle.ConstantTimeCompare for its shared-secret check, eliminating the timing side-channel.
- Admin PSX subprocess endpoints validate date inputs against a strict anchored YYYY-MM-DD regex and execute via argv (exec.CommandContext, no shell), closing argument/command-injection vectors.
- All three container images run as non-root users and use multi-stage builds; PostgreSQL is not published to the host (reachable only on the internal compose network); Postgres has a healthcheck the backend gates on.
- Dependency integrity is locked: Go go.sum is committed and module versions are pinned to maintained, post-advisory lines; the frontend ships a complete lockfile (219 integrity hashes) and the container build uses 'npm ci' for reproducible installs.
- Sensible HTTP server hardening (Read/Write/Idle timeouts, body limit), development-only stack traces, and a request logger that records no bodies, headers, Authorization, or query strings.

4. Detailed Findings
Findings are ordered by severity, then by status (open items first). Remediated and verified-positive items are retained to document the full audit trail.
AUTH-01  Invite and password-reset tokens stored in plaintext in the database
[HIGH]   OPEN   ·   Authentication & Session Management
Unlike refresh tokens (SHA-256 hashed before storage), invite tokens and password-reset tokens are persisted to the users table in raw plaintext and looked up by their raw value. The hashToken() helper is applied only to refresh tokens. This contradicts CLAUDE.md's documented control that invite/reset tokens are 'SHA-256 hashed in DB'. Anyone with read access to the users table (SQL injection, leaked backup, compromised DB credential, read-only replica) can redeem any pending invite (account takeover before first login) or any in-flight password reset (within the 1-hour window). Note that refresh tokens are correctly hashed, so this is a localized gap in an otherwise sound token-storage design.
Remediation: Hash invite and reset tokens with the existing hashToken() (SHA-256) before storing, and hash the incoming token before the lookup in GetByInviteToken / GetByResetToken — exactly as already done for refresh tokens. The email/URL keeps the raw token; the DB only ever holds the hash.
Files: simtrader/internal/auth/service.go, simtrader/internal/user/repository.go, simtrader/migrations/001_create_users.sql
AVAIL-01  Reconciler order fills are not transactional — partial failure leaves cash/position state inconsistent
[HIGH]   OPEN   ·   External Integration & Availability
RunForChallenge mutates participant cash and positions across multiple independent repository calls with no surrounding DB transaction; every repo method executes directly against the shared pool. For a buy, UpdateCash, then updatePosition, then FillOrder are three-plus separately-committed statements. If a later step fails (DB error, timeout, or the 5-minute context expiring mid-loop), earlier writes are already committed: cash can be deducted without shares being granted, or position/cash can move while the order stays 'pending' and is filled again on the next reconcile (double-charge). The double-fill is aggravated because FillOrder issues UPDATE ... SET status='filled' WHERE id=$1 with no 'AND status=pending' guard, so re-processing always succeeds. For a graded paper-trading competition this corrupts balances and the leaderboard.
Remediation: Wrap each order's fill (cash update + position upsert + order status update) in a single pgx transaction (BeginTx/Commit/Rollback), threading the tx through the repo methods so an order either fully fills or not at all. Add 'AND status=''pending''' to the FillOrder UPDATE and check rows-affected to close the double-fill window.
Files: simtrader/internal/challenge/reconciler.go, simtrader/internal/challenge/repository.go
AVAIL-02  Reconciler can run concurrently for the same date/challenge (no idempotency guard or lock)
[HIGH]   OPEN   ·   External Integration & Availability
Reconciliation is triggerable from three sources with no mutual exclusion: the nightly goroutine at 16:35 PKT, the internal EOD-prices webhook (which spawns a reconcile goroutine on every ingest), and AdminReconcile (direct). Because psx_tracker pushes prices right around the EOD window, the webhook-triggered run and the scheduled run can execute simultaneously for the same date, and admin reconcile can fire at any time. ListPendingOrders does a plain SELECT WHERE status='pending' with no FOR UPDATE, and FillOrder has no status guard, so two concurrent runs both read and both fill the same pending order — double-spending cash/shares. Combined with the non-transactional fills above (AVAIL-01), this is a concrete double-fill path, not a theoretical one.
Remediation: Serialize reconciliation with a sync.Mutex on the Reconciler or a Postgres advisory lock keyed by challenge+date. Make the fill atomic with 'UPDATE challenge_orders SET status=''filled'',... WHERE id=$1 AND status=''pending''' and check rows-affected (zero => already filled). Combined with per-order transactions this makes reconciliation idempotent.
Files: simtrader/internal/challenge/reconciler.go, simtrader/internal/challenge/handler.go, simtrader/internal/challenge/repository.go
INFRA-01  No TLS termination anywhere in the deployment topology
[HIGH]   OPEN   ·   Infrastructure & Containers
The entire shipped stack speaks plaintext HTTP. The frontend nginx listens on port 80 only and is published as 80:80; there is no HTTPS listener, no certificate mounting, no ACME/Let's Encrypt sidecar, and no documented external reverse proxy. JWT access/refresh tokens, login credentials, and the admin password all traverse the wire in cleartext for any client connecting to the published port. For an internet-facing university deployment this exposes credentials and session tokens to network eavesdropping and session hijacking. CORS is also configured with AllowCredentials: true, which is only meaningful and safe over TLS.
Remediation: Terminate TLS before traffic reaches the app: add a reverse proxy (Traefik or Caddy with automatic ACME, or an nginx 443 server block with mounted certificates), redirect 80->443, and publish only 443. Set Strict-Transport-Security and ensure tokens are sent only over HTTPS. If an external TLS terminator is assumed to sit in front in the target environment, document that assumption explicitly.
Files: simtrader-frontend/nginx.conf, docker-compose.yml, simtrader/cmd/server/main.go
SECRET-01  psx_tracker config.py still ships an insecure INTERNAL_SECRET default ('dev-internal-secret')
[HIGH]   OPEN   ·   External Integration & Availability
While the Go backend now requires INTERNAL_SECRET with no default, the Python tracker still reads INTERNAL_SECRET = os.getenv("INTERNAL_SECRET", "dev-internal-secret"). If the secret is not exported in the tracker's environment, it silently authenticates to /api/internal/eod-prices with the well-known default. That endpoint ingests EOD prices and synchronously spawns reconciliation that moves student cash/positions, so a guessable shared secret on the tracker side undermines the constant-time check on the Go side. Even when the two sides differ, the silent default masks misconfiguration: the tracker gets a 401, swallows it in a best-effort try/except, and data silently never ingests with only a stdout warning.
Remediation: Make INTERNAL_SECRET required in psx_tracker/config.py (read with no default; exit at import if unset). Never ship a guessable default for an auth secret. Rotate any secret that was ever 'dev-internal-secret'. Surface a 401 from the push distinctly from a network failure so misconfiguration is loud.
Files: psx_tracker/config.py, psx_tracker/fetcher.py, simtrader/internal/config/config.go
INFRA-02  Default admin (admin@simtrader.app / ChangeMe123!) still ships and boots when ADMIN_* env vars are unset
[HIGH]   PARTIAL   ·   Infrastructure & Containers
Admin credentials are configurable via ADMIN_EMAIL/ADMIN_PASSWORD and bcrypt-hashed at runtime (an improvement). However entrypoint.sh fails open: if those vars are unset it only prints a warning and boots with the seeded default admin account active. Migration 001 ships a known bcrypt hash for 'ChangeMe123!' on a status='active' admin, and the credentials are published in README files, so the default credential is publicly derivable rather than merely guessable. ADMIN_EMAIL/ADMIN_PASSWORD are not present in .env.example, so an operator copying the documented environment will not set them and will ship a fully-privileged admin account with a known password on an internet-facing instance. This is a real account-takeover path.
Remediation: Make ADMIN_EMAIL/ADMIN_PASSWORD mandatory when ENV=production (exit non-zero if unset, mirroring requireEnv), or generate a random admin password on first boot and print it once. Add both vars to .env.example with explicit 'must change' guidance, and remove the hard-coded default password hash from the seed migration (or seed the admin as 'blocked' until configured).
Files: simtrader/entrypoint.sh, simtrader/migrations/001_create_users.sql, docker-compose.yml, .env.example, README.md
SECRET-05  INTERNAL_SECRET now required at startup with no insecure default (remediated)
[HIGH]   REMEDIATED   ·   Authorization & Access Control
Previously INTERNAL_SECRET defaulted to a guessable literal 'dev-internal-secret', which would authenticate the EOD ingestion webhook in any environment that forgot to set it. The current Go code requires it via requireEnv with no fallback: an unset value is appended to the missing[] slice and Load() returns an error that main.go treats as fatal, so the server refuses to boot. ENV also now defaults to 'production'. (Note the Python tracker side still ships the insecure default — see SECRET-01.)
Remediation: No action needed on the Go side. Confirmed fixed. Close the corresponding Python-side default (SECRET-01).
Files: simtrader/internal/config/config.go, simtrader/cmd/server/main.go
SECRET-06  .env files are gitignored and no real secret is tracked in git (remediated/verified)
[HIGH]   REMEDIATED   ·   Secrets & Configuration Management
No .env containing real secrets is tracked or has ever been committed; only placeholder .env.example files are in version control. Verified via direct git commands: ls-files shows only three .env.example files, git log --all for .env paths returns empty, and check-ignore confirms simtrader/.env is ignored. The root .gitignore covers .env variants, *.db, *.sqlite, and *.rar.
Remediation: No action required. Confirmed. (See DATA-05 for the minor working-tree cleanup still outstanding and the missing generic .env.* glob.)

AUTH-02  Invite tokens never expire (no expiry column or check)
[MEDIUM]   OPEN   ·   Authentication & Session Management
The invite email states the link 'expires in 7 days' but no enforcement exists. The users table has no invite-token expiry column (only reset_expiry exists), and GetByInviteToken filters only on status='pending' with no time check, so an invite token remains valid indefinitely until the student registers. A pending invite that is intercepted (forwarded email, mailbox compromise, shoulder-surfed link, or — combined with AUTH-01 — a DB leak) can be redeemed months later. Reset tokens, by contrast, are correctly expired after 1 hour.
Remediation: Add an invite_expiry TIMESTAMPTZ column, set it at invite time (NOW()+7d to match the email copy), and add 'AND invite_expiry > NOW()' to GetByInviteToken. Provide an admin re-invite path to mint a fresh token when one lapses.
Files: simtrader/internal/user/repository.go, simtrader/internal/auth/service.go, simtrader/migrations/001_create_users.sql
AVAIL-03  PSX scraper silently degrades to empty data on layout change or partial outage, with no alerting
[MEDIUM]   OPEN   ·   External Integration & Availability
Every parse-failure path in the scraper returns an empty list rather than an error (missing headers, neither DATE nor TIME column found i.e. PSX redesign, or any HTTP error), and _fetch_active_symbols returns an empty set on any RequestException. fetch_day then records the run as 'ok' with zero rows unconditionally, even when PSX changed its HTML or was down, and the push short-circuits on no rows so the reconciler quietly fills nothing or snapshots stale prices. The only observability is print() to stdout — no retry, no escalation, no expected-vs-actual symbol-count sanity check. This is an availability/data-integrity gap (silent multi-day gaps) rather than a direct security flaw.
Remediation: Treat zero/near-zero rows as failure: log the run as 'error' and emit an alert (non-zero exit / email / health metric) when total_rows is 0 or far below the known ticker count. Distinguish market-closed/holiday from parse-broke using the holiday calendar. Add a header-shape assertion that fails loudly when expected OHLCV columns disappear.
Files: psx_tracker/fetcher.py
DEP-01  Python dependencies are completely unpinned with no lockfile or hash verification
[MEDIUM]   OPEN   ·   Dependencies & Supply Chain
psx_tracker/requirements.txt lists six packages with no version constraints, no lockfile, and no hash pinning, and the Docker build runs 'pip install --no-cache-dir -r requirements.txt', so every build resolves each dependency to whatever is latest on PyPI at build time. This makes builds non-reproducible and exposes the pipeline to a supply-chain / dependency-confusion attack: a compromised or typosquatted release of any package (especially the niche, low-popularity psx-data-reader) would be silently pulled into the image that holds INTERNAL_SECRET and posts to the backend. Running as non-root does not mitigate a poisoned dependency executing in-process with the secret.
Remediation: Pin every package to an exact version and generate a hash-pinned lockfile (pip-compile --generate-hashes or uv pip compile); build with 'pip install --require-hashes'. Vendor or vet psx-data-reader given its small maintainer footprint. Add pip-audit (or Dependabot for Python) to CI.
Files: psx_tracker/requirements.txt, psx_tracker/Dockerfile
NET-01  Public internet-facing /api/internal/eod-prices has no rate limiting and is reachable through the nginx proxy
[MEDIUM]   OPEN   ·   Network Exposure & CORS
The internal EOD ingestion route is registered on the root app with no auth middleware, relying solely on the X-Internal-Secret constant-time check. Because nginx proxies all /api/ paths to the backend, this endpoint is reachable from the public internet via the frontend's published port 80, not just from the internal psx_tracker container. The auth limiter does not cover it (it only covers four /api/auth/* routes), so an attacker can spray the internal secret without throttling. The constant-time compare prevents timing leaks but does not prevent unlimited online guessing or resource abuse — each successful call spawns a background reconciler goroutine.
Remediation: Either move internal ingestion off the public path (a separate internal-only listener/port not proxied by nginx, or restrict nginx location = /api/internal/ to the docker network/psx_tracker source), and/or apply a strict rate limiter to /api/internal/*. Combine with IP allow-listing since the only legitimate caller is psx_tracker.
Files: simtrader/internal/challenge/handler.go, simtrader-frontend/nginx.conf, simtrader/cmd/server/main.go
NET-02  No security response headers (HSTS, X-Frame-Options, CSP, X-Content-Type-Options); FACULTY_QNA falsely claims they exist
[MEDIUM]   OPEN   ·   Network Exposure & CORS
Neither the Go backend nor the nginx frontend sets any security response headers — main.go installs only recover, logger, and cors middleware (no helmet), and nginx.conf contains zero add_header directives. Consequences for an internet-facing deployment: no HSTS (downgrade exposure), no clickjacking protection, no MIME-sniffing protection, and no CSP to constrain XSS. Additionally FACULTY_QNA.md claims 'We set Content-Security-Policy headers and X-Frame-Options: DENY on the backend' — false relative to current code, a documentation/reality gap that could give reviewers false assurance.
Remediation: Add fiber helmet middleware (HSTS with max-age >= 1 year + includeSubDomains, X-Frame-Options: DENY or CSP frame-ancestors 'none', X-Content-Type-Options: nosniff, Referrer-Policy, and a Content-Security-Policy), and/or add the equivalent add_header directives in nginx.conf (HSTS only over TLS). Correct the FACULTY_QNA.md claim to match actual behavior.
Files: simtrader/cmd/server/main.go, simtrader-frontend/nginx.conf, FACULTY_QNA.md
SECRET-02  Local simtrader/.env on disk contains real plaintext secrets in a OneDrive-synced folder
[MEDIUM]   OPEN   ·   Secrets & Configuration Management
The working-tree file simtrader/.env (correctly untracked and gitignored) contains a real PostgreSQL password in DATABASE_URL, real 64-byte JWT access/refresh secrets, ENV=development, and INTERNAL_SECRET=dev-internal-secret. It is never committed, but it is a live secrets-on-disk hygiene risk: the secrets are readable by anyone with access to the developer machine, and because the folder is OneDrive-synced they replicate to cloud storage. ENV=development locally also re-enables permissive CORS reflection and stack traces. If any of these secrets are ever reused in a deployed environment, tokens could be forged.
Remediation: Treat the JWT secrets and DB password in this file as compromised: rotate them and never reuse them in any deployed environment. Avoid storing real .env secrets inside a cloud-synced folder; move the repo to a local-only path or use a secrets manager. Set ENV=production locally unless actively debugging, and replace 'dev-internal-secret' with a random 32-byte value even locally.
Files: simtrader/.env, simtrader/.gitignore
CORS-01  CORS reflects any origin with credentials when ENV=development (latent misconfiguration risk)
[MEDIUM]   PARTIAL   ·   Network Exposure & CORS
The CORS middleware sets AllowCredentials: true and AllowOriginsFunc returns true for any origin whenever cfg.Env == 'development'. Reflecting an arbitrary origin together with credentials is the classic reflect-any-origin + credentials misconfiguration. ENV now defaults to 'production' and docker-compose.yml explicitly sets ENV: production, so this branch is inert in the shipped configuration — hence partially-remediated and safe by default. The residual is a latent code-level footgun: if ENV is ever set to 'development' on an internet-facing host (copied dev .env, staging template), the API would reflect any origin with credentials, and the same flag also ungates recover stack traces. Verification confirmed a typo in the ENV value fails closed to production (exact-string comparison), so only a deliberate 'development' value activates the risk. Real-world impact is further reduced because SimTrader uses Bearer tokens in localStorage rather than cookies, so an attacker page cannot ride an ambient cookie. This finding consolidates multiple per-dimension observations of the same code.
Remediation: Even in development, reflect only an explicit allowlist (localhost + known LAN range) rather than returning true unconditionally, or never combine wildcard reflection with AllowCredentials. Gate the dev behavior behind an explicit flag (e.g. CORS_ALLOW_ANY=true) and log a loud startup warning when permissive CORS is active.
Files: simtrader/cmd/server/main.go, simtrader/internal/config/config.go, docker-compose.yml
DATA-01  Seeded default admin password publicly known and not gated by a production startup check
[MEDIUM]   PARTIAL   ·   Data Handling & Privacy
Migration 001 seeds an admin account with the well-known password 'ChangeMe123!' (bcrypt hash committed in SQL, status active). entrypoint.sh overrides it via ADMIN_EMAIL/ADMIN_PASSWORD only if both are set; otherwise it warns and boots with the default. If migrations are applied without the entrypoint override (manual psql, or env vars unset), an internet-facing instance ships with admin@simtrader.app / ChangeMe123!. Because the admin role can read every student's name and email, this is a data-handling exposure as well as an access-control one. (This is the data-privacy view of the same defect as INFRA-02.)
Remediation: Add a startup check that refuses to run in production if the default admin hash is still present, or remove the live hardcoded hash from the migration and require ADMIN_PASSWORD on first boot. Ensure the entrypoint always rotates the seeded password before exposing the server.
Files: simtrader/migrations/001_create_users.sql, simtrader/entrypoint.sh
NET-03  Auth rate limiter keys on c.IP() without trusted-proxy config — collapses to one global bucket behind nginx; /refresh and /logout unthrottled
[MEDIUM]   PARTIAL   ·   Network Exposure & CORS
The 10 req/min/IP limiter covers login, register, forgot-password, and reset-password (a genuine improvement) but not /api/auth/refresh or /api/auth/logout, leaving room for refresh-token grinding. More importantly, the limiter keys purely on c.IP() while fiber.New sets no ProxyHeader and does not enable trusted-proxy checking. Behind nginx (which sets X-Real-IP), Fiber ignores the forwarded header, so c.IP() resolves to the nginx container's address for every request. That collapses the per-client limiter into a single global 10 req/min bucket: one abusive client can exhaust the quota and lock out all users (DoS), and distributed attackers all appear as the same proxy IP.
Remediation: Configure Fiber with ProxyHeader: "X-Real-IP" (or X-Forwarded-For) and EnableTrustedProxyCheck with the nginx/docker network as a trusted proxy, so the limiter keys on the true client IP. Add a dedicated limiter on /api/auth/refresh and a looser global limiter.
Files: simtrader/internal/auth/handler.go, simtrader/cmd/server/main.go, simtrader-frontend/nginx.conf
AUTHZ-03  Internal EOD webhook uses constant-time secret comparison (remediated)
[MEDIUM]   REMEDIATED   ·   Authorization & Access Control
The /api/internal/eod-prices endpoint compares the X-Internal-Secret header using crypto/subtle.ConstantTimeCompare instead of ==, removing the timing side-channel. Combined with the now-required INTERNAL_SECRET (SECRET-05), the secret check itself is adequately protected. (Public reachability and lack of rate limiting on this route remain open as NET-01.)
Remediation: No action needed for the comparison itself. Optionally add IP allow-listing or mTLS for defense-in-depth (see NET-01).
Files: simtrader/internal/challenge/handler.go, simtrader/cmd/server/main.go
CONFIG-01  ENV defaults to 'production' instead of 'development' (remediated)
[MEDIUM]   REMEDIATED   ·   Secrets & Configuration Management
The default value of ENV was changed from 'development' to 'production'. This is the safe default and disables development-only behaviors (recover stack traces, permissive CORS reflection) when ENV is unset. Downstream this gates EnableStackTrace and the CORS reflection function.
Remediation: No action required. Confirmed fixed. (The dev-only CORS code path still exists and is tracked as the latent CORS-01.)
Files: simtrader/internal/config/config.go, simtrader/cmd/server/main.go
AUTH-03  No server-side password strength/complexity policy beyond 8-char minimum
[LOW]   OPEN   ·   Authentication & Session Management
Registration and password reset enforce only a length >= 8 check, with no common-password denylist, no maximum length cap, and no complexity guidance. For an internet-facing deployment, combined with the (effectively global) auth rate limit, trivial passwords like 'password' or '12345678' are accepted. bcrypt also silently truncates inputs beyond 72 bytes, so an unbounded password field can mislead users into a false sense of strength.
Remediation: Raise the minimum to 12, add a check against a small common-password denylist (or zxcvbn-style scoring), and cap length at 72 bytes (or pre-hash before bcrypt) to avoid silent truncation. Apply the same policy in both registration and reset paths.
Files: simtrader/internal/auth/handler.go
AUTH-05  WebSocket access token passed in query string (?token=) — exposed in fronting-proxy logs
[LOW]   OPEN   ·   Authentication & Session Management
The WebSocket endpoint authenticates via a ?token=<accessToken> query parameter. The token is validated correctly with the same parser as Bearer, so this is not an auth bypass. The residual risk is exposure: query strings are routinely written to reverse-proxy/load-balancer access logs, browser history, and Referer headers. The app's own Fiber logger uses ${path} (no query string), so the leak risk is in fronting infrastructure, not the app. This is a largely unavoidable limitation of the browser WebSocket API (no Authorization header), but blast radius should be minimized.
Remediation: Keep access tokens short-lived (already 15m). Consider issuing a single-use, short-TTL WebSocket ticket via an authenticated POST and passing that opaque ticket in the query string instead of the full JWT, so any log leak exposes only a one-time sim-scoped value. Configure fronting proxies not to log query strings.

5. Prioritized Recommendations
1. Terminate TLS before exposing the platform (INFRA-01). Place a reverse proxy with automatic certificates (Traefik/Caddy) or an nginx 443 block in front, redirect 80->443, publish only 443, and enable HSTS. No internet-facing deployment carrying JWTs and credentials should go live without this.
2. Eliminate the publicly-known default admin (INFRA-02 / DATA-01). Make ADMIN_EMAIL/ADMIN_PASSWORD mandatory when ENV=production (fail startup if unset) or generate a random password on first boot, add them to .env.example with 'must change' guidance, and remove the hard-coded default hash from the seed migration.
3. Make the Challenge reconciler transactional and idempotent (AVAIL-01, AVAIL-02). Wrap each fill (cash + position + order status) in a single pgx transaction, add 'AND status=''pending''' to FillOrder with a rows-affected check, and serialize reconciliation with a mutex or Postgres advisory lock keyed by challenge+date. This protects the integrity of graded balances and the leaderboard.
4. Require INTERNAL_SECRET on the Python tracker (SECRET-01). Remove the 'dev-internal-secret' default in psx_tracker/config.py, exit at import if unset, rotate any secret ever set to the default, and surface a 401 from the push distinctly from a network error.
5. Hash invite and reset tokens in the database (AUTH-01) using the existing hashToken() helper, hashing on both store and lookup, so a DB read cannot be used for account takeover. Aligns the code with the documented control.
6. Protect and relocate the internal ingestion endpoint (NET-01). Restrict /api/internal/* at nginx to the docker network / psx_tracker source (or bind it to a non-proxied internal port) and add a strict rate limiter; combine with IP allow-listing.
7. Add security response headers (NET-02) via fiber helmet and/or nginx add_header (HSTS, X-Frame-Options/CSP frame-ancestors, X-Content-Type-Options: nosniff, Referrer-Policy, CSP), and correct the false claim in FACULTY_QNA.md.
8. Fix the rate-limiter proxy configuration (NET-03). Set Fiber ProxyHeader and trusted-proxy checking so the limiter keys on the real client IP rather than the nginx address, and add a limiter to /api/auth/refresh.
9. Pin and lock Python dependencies with hashes (DEP-01) and add automated vulnerability scanning across all three ecosystems (DEP-03: govulncheck, npm audit, pip-audit, or Dependabot/Renovate).
10. Harden operational robustness of the data pipeline (AVAIL-03, AVAIL-04): treat zero/near-zero scraped rows as failures with alerting, assert the expected OHLCV header shape, schedule in an explicit Asia/Karachi timezone, and bound/resume catch-up backfills.
11. Address remaining hardening and hygiene items: add an invite-token expiry (AUTH-02), guard the leaderboard rune-slice panic and add field length caps (INPUT-01), validate avatar file bytes and serve /uploads with nosniff (INPUT-02), enforce DB sslmode in production (DATA-03), add a token/PII retention cleanup job (DATA-04), guard compose secrets with the ':?' form (SECRET-03), and rotate the secrets in the local OneDrive-synced .env (SECRET-02).
12. Anonymize the simulation leaderboard for students to match the challenge design (AUTHZ-01), and apply the lower-priority items (CORS dev-path allowlist, container/image hardening, fail-fast on malformed durations) as time permits.
6. Conclusion
SimTrader is a well-constructed educational platform with a security foundation that is, in most respects, above what is typical for a student/lab project: parameterized database access throughout, bcrypt password hashing at cost 12, a correctly designed JWT and refresh-token lifecycle, a fail-closed authorization model with no privilege-escalation path, non-root containers, and secrets sourced from the environment and kept out of version control. The audit also confirmed that several previously identified weaknesses were remediated during this cycle, including the removal of an insecure shared-secret default on the backend, a switch to constant-time secret comparison, and defaulting the runtime environment to production. The platform handles no real money, no payment data, and only minimal PII, which appropriately limits the worst-case impact of the remaining issues.
That said, the open findings are real and several are material for an internet-facing deployment. The most important are the absence of TLS termination, a publicly known default admin credential that still ships and boots when admin environment variables are unset, an insecure secret default that persists on the Python tracker, and non-transactional, non-idempotent reconciliation logic that can corrupt simulated balances. We assess the overall residual risk as Elevated on the strength of these open items; none are exotic, and all are closable with focused configuration and bounded code changes. We recommend that the TLS, default-admin, tracker-secret, and reconciliation items (recommendations 1–4) be completed before the platform is exposed beyond the lab network, with the remaining hardening items scheduled shortly thereafter. With those changes in place, SimTrader would present a Moderate-to-Low residual risk profile suitable for institutional deployment. This was a static, code-level internal audit; we further recommend a dynamic/penetration test of the deployed environment as a confirmatory step prior to broad rollout.
